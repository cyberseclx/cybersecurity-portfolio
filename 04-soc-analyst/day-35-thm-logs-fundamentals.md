## What Is a Log?

A log is a time-based record of an activity generated by a system, application, service, or security device. Logs can capture both legitimate and malicious activity. An individual entry may provide only one clue, so analysts often correlate multiple records to understand what happened.

Useful investigation questions are:

```text
Who performed the activity?
What happened?
When did it happen?
Where did it originate?
Was the action successful?
What evidence should be checked next?
```

## Main Uses of Logs

| Use case | Security or operational value |
|---|---|
| **Security monitoring** | Detect abnormal or suspicious behaviour. |
| **Incident investigation and forensics** | Reconstruct activity, build a timeline, and support root-cause analysis. |
| **Troubleshooting** | Identify errors and diagnose failures in systems or applications. |
| **Performance monitoring** | Reveal slow responses, resource issues, and service degradation. |
| **Auditing and compliance** | Provide a reviewable trail of actions and changes. |

## Common Log Sources

| Log source | Examples of evidence |
|---|---|
| **Operating system** | Logons, account changes, service activity, errors, and shutdowns. |
| **Application** | User actions, application errors, authentication, and business events. |
| **Web server** | Client IP, HTTP method, requested resource, response status, and user-agent. |
| **Firewall** | Allowed or blocked connections, ports, protocols, sources, and destinations. |
| **Network device** | Interface events, configuration changes, authentication, and traffic-related alerts. |
| **Endpoint/security tool** | Process, file, malware, detection, and response telemetry. |

The source must always be considered before interpreting an entry. The same field or severity label can have different meanings across products.

## Windows Event Logs

Windows Event Viewer organizes records into channels. Three important Windows Logs are:

- **Application:** Events created by applications and services.
- **Security:** Audited authentication, access, and account-management activity.
- **System:** Events generated by Windows system components and drivers.

Useful fields include:

- Date and time
- Log name
- Source or provider
- Event ID
- Level or audit outcome
- User or account
- Computer
- Event-specific details

An Event ID identifies an event type, but it is not a complete conclusion. The analyst must also examine the subject, target, timestamp, outcome, and surrounding events.

## Account-Management Event IDs Used in the Lab

| Event ID | Meaning | Key fields to examine |
|---|---|---|
| **4720** | A user account was created. | Subject account and new/target account. |
| **4722** | A user account was enabled. | Subject account, target account, and event time. |
| **4724** | An attempt was made to reset an account's password. | Subject account, target account, and audit outcome. |

The distinction between **Subject** and **Target/New Account** is important:

```text
Subject account = the account that performed the action
Target/New Account = the account affected by the action
```

The presence of an event should not be treated as proof of success without checking the audit outcome and event details.

## Windows Event Investigation Workflow

1. Open **Event Viewer → Windows Logs → Security**.
2. Filter the current log for the relevant Event ID.
3. Sort by date and time when the question asks for the first or latest event.
4. Open the matching event and separate the subject account from the target account.
5. Record the timestamp, account names, Event ID, computer, and outcome.
6. Search for related events affecting the same account.
7. Place those events in chronological order.
8. Use additional authentication, process, endpoint, or network evidence before deciding whether the activity was malicious.

## Web-Server Access Logs

A web access log records requests received by a web server. Depending on the log format, an entry may contain:

- Source IP address
- Timestamp
- HTTP method such as `GET` or `POST`
- Requested path or resource
- HTTP protocol version
- Response status code
- Response size
- Referrer
- User-agent

Example structure:

```text
SOURCE_IP - - [TIME] "METHOD /requested/path HTTP/1.1" STATUS SIZE "REFERRER" "USER_AGENT"
```

This example shows field placement only and is not copied from the room's lab output.

## HTTP Status-Code Context

| Range | General meaning | Investigation value |
|---|---|---|
| **2xx** | Request succeeded. | The requested action or resource may have been successfully accessed. |
| **3xx** | Redirection. | Follow the redirect path and destination. |
| **4xx** | Client-side error. | Repeated `401`, `403`, or `404` responses may show failed access or enumeration. |
| **5xx** | Server-side error. | May indicate application failure, malformed input, or attack-related disruption. |

A status code alone does not prove malicious activity. It must be interpreted with the requested path, frequency, sequence, source, and normal application behaviour.

## Web-Log Investigation Workflow

1. Establish the investigation time window.
2. Identify high-volume or unusual source IP addresses.
3. Review suspicious methods, paths, parameters, and user-agents.
4. Compare successful and failed requests from the same source.
5. Look for repeated requests, scanning patterns, authentication failures, or access to sensitive resources.
6. Arrange related requests chronologically.
7. Correlate them with application, authentication, firewall, endpoint, or identity logs.
8. Document what the evidence shows and what remains uncertain.

## Guided Lab Takeaways

The guided Windows investigation reinforced that account activity can be reconstructed by correlating events rather than reading one entry in isolation. The key steps were:

- Filter Security logs by the relevant Event ID.
- Identify the most recent account-creation event.
- Distinguish the actor account from the newly created account.
- Locate the related account-enable event and its timestamp.
- Check for a related password-reset attempt.
- Correlate the events into a sequence before drawing a conclusion.

The room also reinforced that web access logs can reveal who contacted a server, which resource was requested, how the server responded, and what should be investigated next.

## Practical Reporting Model

Every investigation should end with four clear statements:

```text
What I checked:
Which log sources, time range, Event IDs, accounts, IP addresses, or paths were reviewed.

What I found:
The relevant events and their sequence.

What it means:
The evidence-supported interpretation, including uncertainty.

What I would do next:
The next log source, host, account, or control to validate.
```

## SOC Relevance

For a junior SOC analyst, log analysis supports:

- Alert validation and triage
- Timeline creation
- User and host scoping
- Authentication and account-change investigation
- Web-attack investigation
- Evidence-based escalation
- Incident documentation and handoff

The goal is not merely to find an unusual entry. It is to connect the entry to its source, context, outcome, related activity, and potential impact.

## Mistakes to Avoid

- Treating one log entry as complete proof of an incident
- Confusing the subject account with the target account
- Ignoring timestamps, time zones, or event order
- Assuming an attempted action succeeded without checking the outcome
- Reading a status code without reviewing the method and path
- Searching only one data source when correlation is possible
- Failing to record the exact evidence supporting a conclusion
- Exposing credentials, private targets, lab answers, or flags in public notes
